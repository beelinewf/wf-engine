## Goal

Add SMTP as a third transport of the existing `external_call` node, alongside `http_config` and `execution_config`, so a workflow can send one templated email per node execution with the same timeout, `output_property`, `on_failure`, and recovery semantics authors already get. Every message field templates from workflow context exactly as HTTP fields do today, and every document that describes `external_call` today is updated in the same change.

## Success Criteria

- A definition with exactly one of `http_config` / `execution_config` / `smtp_config` parses; zero or two-plus transports are rejected at definition time, extending the rule in `parseExternalCallNode` (`internal/workflow/model/nodecontent.go`), which today requires exactly one of two.
- Every `smtp_config` message field templates: `to`/`cc`/`bcc` (each element), `from`, `reply_to`, `subject`, `text`, `html`, and `file.path` all render `{{ path }}` placeholders against the request template data — the same `req.TemplateData()` snapshot (context plus reserved identity roots) that `HTTPExecutor.build` (`internal/workflow/executor/http.go`) renders against; `file.data` values render against that snapshot too, under the file-body rule below. Example that must work end-to-end:
  ```json
  "smtp_config": {
    "to": ["{{ user.email }}"],
    "subject": "Order {{ order.id }} confirmed",
    "text": "Hi {{ user.name }}, total {{ order.total }}.",
    "html": "<p>Hi {{ user.name }}</p>"
  }
  ```
- The HTML body may instead come from a file: `smtp_config.file: {path, data}` supplies the `html` part, so its rendered path must end `.html`/`.htm` (case-insensitive; any other extension is rejected). `file` and inline `html` together are rejected at definition creation — the author chooses one HTML source — while inline `text` may accompany either HTML source, so `text` + `html` and `text` + `file` are both valid. File contents render with the same `{{ path }}` interpolation as inline bodies — explicitly *not* Go `text/template`/`html/template`, so `{{ .Name }}` and `{{ range }}` are render errors — against the rendered `data` map only, never the full workflow context. Example that must work end-to-end:
  ```json
  "smtp_config": {
    "to": ["{{ user.email }}"],
    "subject": "Order {{ order.id }} confirmed",
    "file": {
      "path": "s3://mail-templates/order.html",
      "data": { "name": "{{ user.name }}", "total": "{{ order.total }}" }
    }
  }
  ```
  where `order.html` contains `<p>Hi {{ name }}, total {{ total }}</p>`. Every string leaf of `data` renders against `req.TemplateData()` first (nested objects/arrays included, typed single-placeholder values preserved, as `RenderJSON` in `pkg/contextpath/contextpath.go` does), so the file can name only keys the definition author explicitly mapped; `data` may be omitted only for a placeholder-free file. A file placeholder missing from `data` fails with `render smtp_config.file: …` and nothing is sent.
- A single-placeholder recipient element expands a typed list: `"to": ["{{ team.emails }}"]` where `team.emails` is a context array of strings splices into the recipient list, using the typed-value behavior of `RenderTemplate` (`pkg/contextpath/contextpath.go`: “when the whole string is a single placeholder the typed value is returned”). Interpolated (mixed text) elements stringify with `%v`, exactly as HTTP headers do in `buildConfig` (`internal/workflow/executor/http.go`).
- Rendering failures behave like HTTP: a missing context path fails the node with a wrapped render error (e.g. `render smtp_config.to[0]: …`), never a partial send. All validation (address parse, CR/LF injection, non-empty recipients) runs *after* rendering, mirroring how templated HTTP URLs validate post-render in `buildConfig`; static non-templated values additionally fail fast at parse time, mirroring `validateStaticHTTPURL`.
- On success the node stores a small result (recipients, subject, from — never the body) under `output_property`; any dial/auth/recipient/DATA failure returns a `NodeError` with reason `smtp`, so existing `on_failure` routing for `external_call` (already allowed by `onFailureAllowed` in `internal/workflow/model/nodecontent.go`) handles it with no engine change.
- Definitions still parse when no SMTP relay is configured; execution then fails with a clear “smtp is not configured” error, mirroring the optional-transport pattern in `Dependencies` (`internal/workflow/executor/executor.go`).
- Command templating parity note: today only command `stdin` templates (`internal/workflow/executor/command.go`); argv stays literal so the canonical-path allowlist cannot be bypassed. SMTP has no argv analogue, so *all* SMTP fields template — this matches the HTTP arm, which templates url, method, every header value, and the JSON body.
- Docs parity: every surface listed in step 5 describes the SMTP arm (fields, templating, output shape, relay configuration, hardening) consistently with the served node schema, and no doc still claims `external_call` is “exactly one of `http_config` / `execution_config`”.

## Approach

**Key decision 1 — third arm, not a new node type.** Today `ExternalCallExecutor` (`internal/workflow/executor/nodes.go`) dispatches on `req.Node.HTTP != nil` vs `req.Node.Execution != nil`, and the poller already sets the precedent of one type with exactly-one transport block (`parsePollerNode` in `internal/workflow/model/nodecontent.go`). A separate `smtp` node type was rejected: it would duplicate timeout, `on_failure`, and recovery handling that `external_call` already owns. A `pkg/customnode` node was rejected because the request names `external_call` itself, and custom types are opt-in registrations, not builtins.

**Key decision 2 — relay lives in server config, never in the definition.** This follows the storage rule stated on `InputStorageRef` (`internal/workflow/model/nodecontent.go`: “the endpoint and credentials live in global config, never in a definition”) and the allowlist posture of the HTTP and command executors. Add a new `engine.smtp` block (`host`, `port`, `username`, `password`, `from`, `use_tls`; env `BEELINEWF_ENGINE_SMTP_*`) instead of reusing `auth.local.smtp`: that block is only constructed when local auth *and* email verification are both enabled (`cmd/app/main.go`), so reusing it would make workflow mail silently unavailable in most deployments. Two SMTP configs is a real cost, accepted deliberately; the shared sending code (below) keeps it to config duplication only, and the docs (step 5) must explicitly distinguish the two relays so operators do not conflate them.

**Assumption (reversible — flag it if wrong):** the node supplies only the message (`to`, optional `cc`/`bcc`, optional `from` override defaulting to the relay `from`, optional `reply_to`, `subject`, and `text` and/or `html` bodies or one `file` body under key decision 4), never host, port, or credentials. If you instead want per-node relay settings, say so before `go` — that variant needs an SMTP host allowlist modeled on `engine.http_allowlist` and is a materially larger, riskier change.

**Key decision 3 — generalize the one mail boundary.** `internal/workflow/mail/mail.go` declares itself “the only mail-sending boundary in the engine” but exposes only `SendVerification`. Add a generic `Message{From, To, Cc, Bcc, ReplyTo, Subject, Text, HTML}` and `Send(ctx, Message)` on `SMTPSender`, reusing its existing STARTTLS/implicit-TLS, `PlainAuth`, multipart/alternative + quoted-printable construction, and CR/LF injection checks; `SendVerification` becomes a thin builder over it so verification mail cannot drift from workflow mail. Arbitrary custom headers are out of scope for v1 (injection surface, no stated need). No transparent retry: unlike idempotent HTTP GETs, a retried send duplicates mail, so failures surface to `on_failure` immediately, and `retry_on_recovery` stays default-false for this transport with the duplicate-send risk documented. The fixed 10s `sendTimeout` in the mail package becomes a context deadline supplied by the caller, so the executor enforces the node timeout via the same `nodeTimeout` helper the HTTP and command executors use.

**Key decision 4 — file bodies resolve in the executor, confined by operator config.** `smtp_config.file.path` dispatches on the rendered path: `s3://bucket/key` reads through the global object store, and any other path is a local file under a new operator root `engine.smtp.template_dir` (env `BEELINEWF_ENGINE_SMTP_TEMPLATE_DIR`). Bare `./local.html` therefore means “under `template_dir`”, never the process working directory: local paths must be relative, cleaned, and rejected when they escape the root, because a definition-controlled absolute or traversing path would let any author mail arbitrary host files (starting with the deployment's own config) to any recipient. This mirrors the one existing local-template precedent, `auth.local.smtp.template_dir` in `internal/workflow/mail/templates.go` — an operator directory, never a definition path — while keeping the two knobs distinct: that one overrides the fixed verification pair, this one roots arbitrary workflow body files. For S3, extend `objectstore.Store` (`internal/workflow/objectstore/objectstore.go`), which today is Put/Delete only, with a bounded `Get(ctx, bucket, key)`; the client stays the existing `Infra.Storage` MinIO client built once in `cmd/app/main.go` and reaches the executor via `Dependencies`, so endpoint and credentials never appear in the definition — extending key decision 2, and rejecting per-node S3 credentials of the kind `pkg/customnode/s3fetch` templates from context. The S3 object's content-type metadata is ignored; a file body is always the HTML part, so its rendered path must carry an `.html`/`.htm` extension. The `mail` package stays unaware of files: the executor resolves a file to a rendered string that fills `Message.HTML`, so MIME construction, the never-log-the-body rule, and the body-free `SMTPResult` are unchanged (the result does not gain the path or source either — a templated path is context data). Loading happens per execution under the node timeout, raw and rendered bodies each capped at `MaxOutputBytes`, with no caching in v1: a replaced template takes effect on the next execution. If `template_dir` is empty, local files are disabled; if storage is not configured, `s3://` files are disabled; either way definitions still parse and execution fails with a clear not-configured error, mirroring key decision 2's relay pattern.

## Steps

1. **Model** — In `internal/workflow/model/nodecontent.go`: add `SMTPConfig` beside `HTTPConfig`/`ExecutionConfig` (with a nested `File *SMTPFileConfig` holding `Path string` and raw-JSON `Data`), a `SMTP *SMTPConfig` field on `NodeContent`, `rawSMTPConfig`/`rawSMTPFileConfig` + `smtp_config` on `rawNode`, and extend `parseExternalCallNode` to exactly-one-of-three. Parse-time validation is template-aware: fields containing a placeholder (per `contextpath.HasTemplate`, the check `validateStaticHTTPURL` uses) defer value validation to execution; static values fail fast (non-empty `to`, single-line subject, at least one body source among `text`/`html`/`file`, `net/mail` address checks). Static `file` values additionally fail fast on: non-empty `path`, an `.html`/`.htm` extension when the path is untemplated, any inline `html` alongside `file` (rejected unconditionally at parse time, regardless of templating), and `data` present-but-not-a-JSON-object; `data` keys must be valid bare context keys (per `contextpath.ValidKey`) since file placeholders resolve against them. No file I/O happens at parse time — definitions must parse on hosts where the template may not exist. Add `r.SMTPConfig` to the inline-field rejection lists in `parseReferencedNode` and `parseCustomNode`, exactly where `HTTPConfig`/`ExecutionConfig` already appear. Update `externalCallNodeSchemaJSON` in `internal/workflow/model/nodeschema_docs.go` with the `smtp_config` property (documenting that every string templates, plus the `file` object: alternative HTML source to inline `html` and mutually exclusive with it, `{{ path }}`-only rendering against `data` alone, local paths confined to `engine.smtp.template_dir`, `s3://` paths read via global storage) and a third `oneOf` arm — this constant is the served schema documentation, so it is part of both this step and step 5. → verify: step 1 tests in Validation Plan.
2. **Mail package** — Refactor `internal/workflow/mail/mail.go`: extract envelope+MIME sending into `Send(ctx, Message)`; validate every rendered address/subject field for CR/LF and parseability; keep verification behavior byte-compatible, and add a log implementation of the generic send that logs recipients and subject only, never bodies. → verify: existing `mail` tests pass untouched.
3. **Executor** — New `internal/workflow/executor/smtp.go` with a `buildSMTPMessage` step paralleling `buildConfig`: render `from`/`reply_to`/`subject`/`text`/`html` with `contextpath.RenderTemplate` against `req.TemplateData()` and require string results; render each recipient element, splicing a typed `[]string`/`[]any` result when the element is a lone placeholder and stringifying otherwise; wrap failures as `render smtp_config.<field>: …`. When `file` is set, resolve it in a `loadSMTPFileBody` step: render `file.path` (string required) and re-check the `.html`/`.htm` extension post-render (the `file` + inline `html` conflict was already rejected at parse time); render `file.data` with `contextpath.RenderJSON` against `req.TemplateData()` and require a top-level object (failures wrapped as `render smtp_config.file.data: …`); load the raw template — `s3://bucket/key` via the optional object-reader dependency, otherwise a relative path joined under the configured template root and rejected on escape after symlink resolution; any other `://` scheme is rejected (failures wrapped as `load smtp_config.file: …`, including the not-configured cases) — capping raw bytes at `MaxOutputBytes`; then render the contents with `contextpath.RenderTemplate` against the rendered `data` map only, require a string result, and assign it as the HTML part (failures wrapped as `render smtp_config.file: …`). Then re-validate the rendered message, cap recipients (100) and each body (inline or file-rendered) at `MaxOutputBytes`, set `Date` and a `Message-ID` derived from instance/node-instance ids (not context data), and return a new `SMTPResult` in `internal/workflow/executor/executor.go`. Wire the third dispatch arm in `internal/workflow/executor/nodes.go`, add relay settings plus the template root to `Limits` and an optional sender plus an optional template object-reader (the `objectstore.Store` `Get` from step 4) to `Dependencies`, and build it in `NewExecutors` with fail-fast startup validation like `NewCommandExecutor`. → verify: step 3 tests.
4. **Config and wiring** — Add `Engine.SMTP` to `pkg/configuration/configuration.go` with load-time validation mirroring `NewSMTPSender`, including `template_dir` (env `BEELINEWF_ENGINE_SMTP_TEMPLATE_DIR`; when set it must name an existing directory at boot, mirroring how `loadVerifyTemplates` fails construction on a broken override); map it in `executorLimits` (`cmd/app/main.go`); extend `objectstore.Store` with `Get` (MinIO `GetObject`, read capped by the caller) and pass the already-built `objStore` into `NewExecutors`' `Dependencies` in `cmd/app/main.go`; document `engine.smtp` (including `template_dir` and the `s3://` requirement that `infra.storage` be configured) in `config.yaml` and the e2e configs (Mailpit in `docker-compose.yml` already provides a catch-all relay). Audit `pkg/envsnapshot`: the deny list documented in `config.yaml` covers `BEELINEWF_AUTH_*` but not a new `BEELINEWF_ENGINE_SMTP_PASSWORD`, which would otherwise be snapshotted into workflow context — and once in context, templatable into a mail body — so extend the deny patterns and add a test. → verify: step 4 tests.
5. **Related docs** — Update every surface that documents `external_call` today, in the same change:
   - `docs/integration/fields.md` — the `external_call` row (“exactly one of…”, templating column, output column), the output-shape list (`external_call` smtp → `{To, Cc, Bcc, From, Subject}`), the `file` body contract (file as the HTML source mutually exclusive with inline `html`, `data`-only `{{ path }}` rendering, `template_dir` confinement, `s3://` via global storage, no body/path in output), plus the `on_failure` and referenced-node rejection mentions if their field lists change.
   - `README.md` — node-type table row, feature bullets, configuration table (add `engine.smtp.*` beside `engine.http_allowlist`/`engine.exec_allowlist`), and hardening notes (relay must be authenticated/internal, `use_tls` on, password via `BEELINEWF_ENGINE_SMTP_PASSWORD` never committed — cross-referencing the existing `auth.local.smtp` secret guidance without conflating the two relays; local body files confined to `engine.smtp.template_dir`, distinctly from `auth.local.smtp.template_dir`).
   - `workflow.yaml` — header comments and the `external_call` example block; add a templated `smtp_config` example following the commented `execution_config` example precedent, plus a commented `file`-body variant showing both a `template_dir`-relative local path and an `s3://` path with a `data` map.
   - `docs/custom-nodes.md` — add `smtp_config` to the builtin-executable-field rejection lists that already name `http_config`.
   - `docs/integration/endpoints.md` and `api/openapi.yaml` — only if their `external_call`/`on_failure` wording or node-content description changes; the type enum itself does not (type stays `external_call`).
   - Swagger artifacts (`docs/docs.go`, `docs/swagger.json`, `docs/swagger.yaml`) are generated (`task swagger` runs `swag init` per `Taskfile.yaml`): regenerate only if Go doc comments or DTOs are touched, and never hand-edit them.
   → verify: docs checks in Validation Plan.
6. **No other surfaces** — No migration, no new API endpoint, no frontend change in this plan; the generic frontend picks up `smtp_config` from the served node schema (step 1) automatically.

- `go test ./internal/workflow/mail/` — existing suite unmodified (proves the refactor is behavior-preserving), plus generic `Send` cases for cc/bcc, text-only, and html-only messages.
- `go test ./internal/workflow/executor/ -run 'SMTP|ExternalCall'` — delivery against an in-test fake SMTP server modeled on `internal/workflow/mail/mail_test.go`: envelope recipients; templated `to` from context, typed-list expansion of `"{{ team.emails }}"`, interpolated subject/body; missing-path render error with no DATA sent; CR/LF injected via a rendered subject rejected; STARTTLS-downgrade refusal; unconfigured-relay error; timeout enforcement. File cases against a temp `template_dir` and a fake object-reader: local `.html` and `s3://` `.html` bodies delivered as the HTML part, file + inline text delivered as both parts; `data` values rendered from context while a file placeholder naming a context path directly (`{{ user.name }}` with no `data` key) fails with no DATA sent; Go-template syntax (`{{ .Name }}`) fails; `../` escape and absolute local paths rejected; templated path resolving to an unsupported extension rejected; oversized raw file rejected; missing local file and missing S3 object wrapped as `load smtp_config.file: …`; unconfigured `template_dir` / unconfigured storage errors. **This fake-relay templated-delivery test is the highest-risk check** — it is the only one proving model, templating, and mail layers compose.
- `go test ./internal/workflow/engine/ -run OnFailure` style case (following `internal/workflow/engine/engine_flow_test.go`) — SMTP failure routes to `on_failure`; success writes only the `SMTPResult` shape to context.
- `go test ./pkg/configuration/ ./cmd/app/ -run 'SMTP|ExecutorLimits'` (including `BEELINEWF_ENGINE_SMTP_TEMPLATE_DIR` binding and boot rejection of a non-directory `template_dir`), `go test ./internal/workflow/objectstore/ -run Get` for the new bounded read, then `go build ./...` and the repo’s configured lint gate (`.golangci.yml`), then the full `go test ./...` if the budget allows.

## Risks / Open Questions

- **Duplicate sends:** SMTP has no idempotency; a recovery requeue or author-set `retry_on_recovery: true` can deliver twice. Mitigated only by the deterministic `Message-ID` for downstream dedup — called out in the node schema description and in `fields.md`.
- **Recipient abuse:** v1 has no recipient allowlist; any definition author can mail any address through the operator relay. Accepted for v1 because authors already reach allowlisted HTTP targets, but if that trust level is wrong, the follow-up is an `engine.smtp.allowed_recipient_domains` list — say so and it becomes a step 1/4 addition rather than a redesign.
- **Secret leakage:** the relay password must never reach workflow context (env-snapshot audit in step 4) and the result must never echo bodies (step 3); both are test-pinned. Templating cuts the other way too: any context value, including the `secret` root, can be mailed by design — same trust posture as templated HTTP bodies today, and stated explicitly in the docs.
- **File-source exposure:** a `file` body can mail any file under `engine.smtp.template_dir` and any object in any bucket the global storage credentials can read — there is no per-bucket or per-file allowlist in v1, so operators must scope the storage credentials and the template root to mail content only. The `data`-only rendering scope limits what context leaks *into* a shared template, but an explicitly mapped `data` value (including from the `secret` root) is mailed by design, as with inline bodies. Templates are loaded per execution with no pinning or caching: replacing a file changes the next send without a definition change, which is the intended authoring flow but means template stores carry the same change-control weight as definitions.
- **Doc drift:** the served schema (`nodeschema_docs.go`) and `fields.md` are both hand-authored; the validation grep checks above are the guard, since no test currently diffs one against the other.
- No blocking open questions under the stated assumption; the per-node-relay alternative above is the one decision to override before `go` if it is what you meant.
